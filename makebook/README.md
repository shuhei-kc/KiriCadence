# KiriCondenser — 定跡修正サイクル

floodgate に放流しながら**対象定跡** (`TargetBook`) を育てるシステム。
1つの**課題局面**につき「前例の取り込み → 自己対局 → 書き出し」を1サイクル
として、タスクを1件ずつ逐次処理する。設計の背景は [DESIGN.md](DESIGN.md)。

## 起動

```bash
py -3.12 makebook\condenser.py
```

BookMiner と同じく「子プロセスとして起動し stdin にコマンドを送る」形なので、
将来 GUI から駆動できる。対局用エンジンとは独立したプロセスで動く。

| コマンド | 意味 |
|---|---|
| `s` | 状態表示 (稼働時間・タスク残・定跡規模) |
| `t <position>` | 課題局面を直接追加 |
| `k <position>` | 棋譜を追加 (そこから課題局面を導出) |
| `set <キー> <値>` | 設定変更 (実行中に変えられるキーのみ。即保存) |
| `show` | 変更可能な設定の一覧 |
| `w` | いま定跡を書き出す |
| `pause` / `resume` | サイクルの一時停止 / 再開 |
| `q` | 終了 (実行中のサイクルの区切りで止まる) |

`t` / `k` の局面は `startpos moves ...` でも `sfen <sfen> moves ...` でもよい。
**すべて cshogi で合法性を検証**してから積むので、打ち間違いは弾かれる
(「3手目 7g7f は非合法です」のように場所を示す)。

## 1サイクルの流れ

### 1. 課題局面を決める

棋譜を**終局側から遡り**、**対象定跡より優先度の高い定跡だけ**を見て、
先後や自分が指したかを問わず「採用手が登録されている最後の局面」を探す。
**そこで実際に指された手を適用した後**が課題局面になる。
採用手の判定はラッパーと同じロジック
(優先度・b/w/x・flip・depth ゲート・deep タイブレーク)。

適用するのは**定跡の採用手ではなく棋譜の手**。定跡手を使うと自分が本線だと
思っている変化ばかり掘ることになり、実際に相手が外してきた変化を調べられない。
**定跡を外されたときも、外した手を適用した後が課題局面**になる
(そここそ調べたい局面なので)。棋譜がその局面で終わっているときだけ
採用手を使う。

外れたかどうかは**候補集合**で判定する — 定跡に複数手が登録されている
局面では、採用手はタイブレークで選ばれた1手にすぎないので、それと
比べると「登録済みの別の候補を指しただけ」まで外れた扱いになってしまう。
ログは候補に無い手なら `※定跡の候補は 7g7f/2g2f = 外された変化`、
候補のうちの1つなら `(定跡の候補2手のうちの1つ)` と出る。

この結果、**課題局面は必ず由来棋譜に現れる**ので、由来棋譜は常に
取り込み対象になる (定跡手を使っていた頃は「課題局面が現れない」で
取り込めないことがあった)。

**対象定跡自身は判定に含めない**。含めると、サイクルが書き足した
深い局面がフロンティアとして拾われ、課題局面が際限なく奥へ移動して
定跡が発散する (学習結果が判定条件に混ざる)。

対象定跡の優先度は `TargetBook` のファイル名先頭3桁から取るので、
設定は1つ (`TargetBook`) だけで整合する。つまり定跡の役割は番号で決まる:

| 優先度 | 役割 |
|---|---|
| 対象より上 (例 000_*) | **フロンティアを定める手作り定跡**。学習では触らない |
| 対象 (`TargetBook`。例 100_x_book.db) | このサイクルで育てる定跡 |
| 対象より下 (例 200_*, 900_*) | 定跡が埋まるまでの受け皿。判定にも自己対局にも使わない |

ある定跡をフロンティアの判定に使いたければ、番号を対象定跡より
小さくする (ファイル名を変えるだけでよい)。

#### 高優先定跡の複製 (閲覧用)

サイクルの頭で、`MergeBookPriority` 以下の定跡 (既定は0番台) を対象定跡へ
複製する。**対象定跡ひとつを開けば全体を追えるようにするため**の複製で、
採用は元のファイル (優先度が上) で行われるので実戦の手順は変わらない。

複製は学習で削られても書き換わっても構わない — 次のサイクルで元の
ファイルから取り込み直される。元の `000_*` は KiriCondenser が書き換えないので、
手作り定跡そのものは常に無傷。既に対象定跡にある指し手は上書きしない
(学習で育てた採用回数を壊さない)。

### 2. 棋譜の取り込み

取り込むのは2種類で、**どちらも同じ規則**で処理する:

1. **由来棋譜** — その課題局面を決めた棋譜自身。放流対局そのものが
   一番効く材料なので捨てない。
2. **csa.db の前例** — 課題局面を含む対局を**新しい順に最大
   `PrecedentGames` 局**。一度取った対局は `state.db` に記録して次回から
   飛ばすので、呼ぶたび自然に古い方へ進む (件数が増えても主キーの
   逆順スキャンなので重くならない)。

各棋譜では**課題局面が最後に現れた手数**から再生し、1手 `AnalysisNodes` で
検討する。評価値が `±DecisiveEval` に達した時点で終局扱いとし、
そこまでの手を**自己対局とまったく同じ規則**で反映する
(実際の対局結果は見ない):

- **勝ち側は加算**。同一局面が区間内に複数回出たときは**最後に出たときの
  指し手だけ**を加算するので、1つの棋譜から同じ局面に2つの手が入らない。
- **負け側は末尾から遡って削除**し、消しても選択肢が残る局面
  (＝本当の分岐点) に当たったところで止める。加算だけだと負け筋が
  定跡に残り続け、候補が増える一方になる。削除規則は自己対局と
  共通の `prune_losing_line` に一本化してある。

削除は対象定跡だけを触るので、高優先の定跡や他の棋譜由来の局面は
影響を受けない。ログは `12手を登録 / 2手を削除` のように出る。

**棋譜が決着しないまま終わったら、その局面から指し継いで決着させる**
(`SelfPlayNodes` / `ResignValue` を使う)。入玉模様など評価値が伸びない
将棋を丸ごと捨てないため。投了値が効くので、既に大差なら数手
(多くは0手) で決まる。指し継いだ手も勝ち側の手として登録される。

0手だったときは理由を表示する (`課題局面が現れない` / `決着せず` /
`勝ち側の登録対象なし` / `棋譜を読めない`)。`課題局面が現れない` は
**前例側だけ**で起きる — 別の対局なのでその局面を通らなかった、という
意味。由来棋譜は課題局面の導出元なので必ず通る。

### 3. 自己対局

課題局面から `SelfPlayNodes` / `ResignValue` で連続対局し、
**どちらかが `WinStreak` 連勝したらサイクル終了**。千日手は既定で後手勝ち
(`DrawWinner`)。学習は makebook4 と同じ規則:

- 勝ち側の指し手は採用回数 +1 (定跡に無ければ追加)
- 負け側は末尾から遡って定跡手を削除し、**消しても選択肢が残る局面**
  (＝本当の分岐点) に当たったところで止める
- 対象より高優先の定跡由来の手は触らない (選択もラッパーと同じロジック)。
  対象より低優先の定跡は自己対局では引かない — そこを学習で埋めて
  上書きさせるのが目的だから

### 4. 書き出し

対象定跡を tmp に書いてから置き換える。SFEN順ソート・
depth 列付きなので、ラッパーがそのまま読める。**ラッパーが対局中に
その定跡を読んでいても衝突しない** (`wrapper/file_swap.py`。Windows では
読み手・書き手の両方を合わせないと PermissionError になる)。ShogiHome が1局ごとに
エンジンを再起動するので、次の対局から反映される。

**採用回数は count 欄 (5列目) に書き、value 欄 には入れない。**
value はエンジンの評価値を入れる欄で、それ以外の量を入れるべきでは
ない (やねうら王は ±32000 = `VALUE_MATE` を詰みとして扱うので、値に大きく
寄与する数を書くと詰みと見分けが付かない)。ラッパーは
**value 最大 → count 最大** の順で選ぶので、makebook4 と同じく
「最も補強された手」が採られる。

## タスクの積まれ方

タスクは `tasks/` に1件1 JSON ファイルとして積まれ、ファイル名順
(マイクロ秒まで含む時刻) に処理される。**サイクル中は取り出さない**ので、
実行中のループに割り込むことはない。完了したものは `tasks/done/`、
失敗は `tasks/error/` へ移る。

投入経路は3つ:

1. **floodgate 対局中の自動投入** — ラッパーが自分の評価値を監視し、
   決着水準に達した瞬間に**実際の終局を待たず**タスクを書き出す
   (1対局につき1回)。ラッパー側 `config.txt` で有効にする:

   ```
   TaskDir            makebook\tasks
   TaskEvalThreshold  1000
   TaskEmitOn         loss
   ```

   既定の `loss` は**自分が負け側になったときだけ**投入する。直したいのは
   負けた定跡であり、勝ち局まで積むとキューが積み上がるため。
   拾いたくなったら `win` / `both` に変えられる。
   評価値は探索の手番側 = 自分から見た値なので、負の値が自分の劣勢を指す
   (ponder 中も根の手番は自分なので符号の意味は変わらない)。
   `go infinite` / `go mate` の検討モードは対局と無関係なので対象外。
   投入されたタスクには `outcome` (`loss` / `win`) が入る。

2. **外部コマンド** (ShogiHome の bat など):

   ```bash
   py -3.12 makebook\push_task.py --kifu "startpos moves 7g7f 3c3d"
   ```

3. **手作業** — KiriCondenser の `t` / `k` コマンド。

タスクが尽きると、csa.db から対局者名に `NameFilters` を含む対局を
新しい順に取り込む。**そのうち対象の名前が負けた対局だけ**を引く
(直したいのは負けた定跡なので、勝ち局を積んでもキューが伸びるだけ)。

**千日手は `DrawWinner` の裏側にとって負け扱い**。既定 (`DrawWinner white`)
では、先手番での千日手は負けとして拾い、後手番での千日手は拾わない
— 先手は千日手を避けたい / 後手は千日手歓迎、というラッパーの方針
(`../DESIGN.md` §5.1) と同じ判断を使う。結果なし (中断) は勝敗が
付いていないので含めない。

`NameFilters` はカンマ区切りで複数指定でき、空にすると自動補充を止める。

積まれたタスクには `outcome: loss` と負けた側 (`loser_side`) が入り、
表示は `csa.db 1062404 敗戦(後手) test_i5-4300U vs Tantalum_Condenser`
のようになる。

## 二重起動の防止

同じ設定の KiriCondenser は同時に1つしか動かない
(`condenser.lock` の OS ロック)。2つ目は起動直後に
「既に別の Condenser が動いています」と出て終了する。
クラッシュしても OS がロックを解放するので、ロックファイルの
手動削除は不要 (残っていても無害)。

**動作中は対象定跡を外から編集しないこと**。停止時の保存で
上書きされる (実際に起きた)。編集したいときは先に `q` で止める。

## 途中で止めたとき

`q` でも強制終了 (プロセスkill・電源断) でも、壊れた状態にはならない。

- **タスクは完了扱いにしない。** 連勝条件に達していないサイクルは
  「中断」として扱い、タスクファイルを `tasks/` に残す。次回起動で
  同じ課題局面をやり直す (完了したものだけが `tasks/done/` へ移る)。
- **前例は処理した分だけ取得済みにする。** 取得しただけで未処理のものは
  `state.db` に記録しないので、次回また引ける。
- **定跡は棋譜1局ごと・自己対局1局ごとに書き出す。** 1サイクルは長い
  (本番設定なら数時間) ので、終了時にまとめて書くと強制終了で全部失う。
  書き出しは tmp → `os.replace` なので、対局中のラッパーが読んでいても
  壊れない。
- 順序は **「定跡を保存してから取得済みにする」**。逆だと落ちたときに
  「前例は消費したのに学習内容は失われた」状態になり、その棋譜を二度と
  引けなくなる。

`q` は実行中の探索を中断してから止まるので、数秒〜1手ぶんの待ちがある。
状態は `s` で確認できる。

**やり直しの副作用**: 中断したタスクを次回やり直すとき、由来棋譜は
もう一度検討される (採用回数が再度 +1 される)。頻繁に止めるとその棋譜の
手がわずかに強く重み付けされる。実害は小さいが、気になるようなら
中断はサイクルの区切りで行うとよい。

## 設定 (config.txt)

やねうら王 Option 系の `名前 値` 形式。相対パスはこのファイルの場所基準。
`show` に出るキーは実行中に `set` で変更でき、その場で保存される。

| キー | 既定 | 意味 |
|---|---|---|
| `CsaDbPath` | `C:\shogi\KiriCompass\data\csa.db` | 前例DB (読み取り専用) |
| `PrecedentGames` | 5 | 1課題局面あたりの前例数 |
| `AnalysisNodes` | 10000000 | 前例検討 1手あたり |
| `DecisiveEval` | 1000 | 終局扱いにする評価値 |
| `SelfPlayNodes` | 50000000 | 自己対局 1手あたり |
| `ResignValue` | 400 | 投了値 |
| `WinStreak` | 5 | サイクル終了に必要な連勝数 |
| `DrawWinner` | white | 千日手の勝者 |
| `MaxPly` | 320 | これを超えたら引き分け扱い |
| `NameFilters` | Condenser | 自動補充する対局者名 (部分一致) |
| `MergeBookPriority` | 0 | この優先度以下の定跡を毎サイクル対象定跡へ複製 (-1 で無効) |

`CsaDbPath` はコードから直接参照せず必ずこのキー経由なので、KiriCompass を
将来 Cadence 内へ移しても1行の変更で済む。

## テスト

```bash
py -3.12 -m unittest discover -s makebook\tests
```

局面キーが実 csa.db と一致することを実データで検証しているので、
KiriCompass 側の仕様が変わったらここが落ちる。
